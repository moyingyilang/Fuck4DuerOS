# U-Boot 全量逆向分析：目标与路线图

> 2026-10-03 立项目标。设备已救回，转入系统性分析阶段。

## 已确立的基础事实（必须遵守）

```
镜像格式      DHTB，头 64 字节，头后 448 字节全零填充
载荷起点      文件偏移 0x200   ★ 曾误判为 0x40，导致 0x1C0 的系统性漏检
载荷末尾      文件偏移 0xe6358
载荷大小      0xe6158 (942,424) 字节
加载基址      0x9f006000
地址换算      abs(off) = 0x9f006000 + (off - 0x200)
```

**验证方式**（必做）：任何新结论都要用端到端对照检验，不能只用同区域类比。

```bash
# 已知字符串必须有引用；载荷相对偏移 = 文件偏移 - 0x200
./adrp_xref uboot_a.img 0x9b2d7    # → ADRP@0x72c8 + ADD@0x72cc
```

## 已确认的关键结论

| 项 | 内容 |
| --- | --- |
| 模式魔数 | `miscdata[0..3]` 小端字：bit0-6 为模式号，bit8-31 须为 `0x53464D`（`'M','F','S'`） |
| 校验函数 | `0x9f038c88` —— 读 miscdata → 校验 → 取模式号 → 查表 |
| 模式表 | `0x9f09a0f0`，12 字节/项，`[+8]` 为启动值 |
| 模式名表 | `0x9f09a2a0`，8 字节/项指针数组 |
| 现状 | 无任何代码写 MFS，故校验恒失败，模式分发永不激活 → 按键被 `w4<=1` 拦住 |
| 按键函数 | Ghidra 中为 `FUN_00005858`（音量上键），模式参数 `w4` 来自上述链路 |

## 方法论（本次教训）

**这个项目已经因为「工具的系统性偏差」犯过一次错**，代价是推翻了正确结论。因此：

1. **验证输入假设**，不要假设格式文档可信。`od` 一行就能发现 0x40~0x200 全零。
2. **阳性对照要端到端**，不能用同区域类比。「另一个字符串有引用」只能证明算子大体可用，不能排除系统性漏检。
3. **阴性结果最多是「不支持」，不能作「否定」**。找不到引用时先怀疑搜索范围与坐标。
4. **每个结论都要留下可复现的验证命令**，写进文档。

### 首批调用链发现

**`0x9f038c88`（读 miscdata 的 MFS 校验函数）只有一个调用者：**

```
0x9f00d2b8  bl → 0x9f038c88
```

该调用者位于函数 `0x9f00d2ac` 内（即打印模式名的那个函数）。

**但对 `0x9f00d2ac` 本身：**

```
BL/B 调用者    0 个
8 字节绝对指针  0 个
```

⇒ `0x9f00d2ac` **可能是死代码**（无任何可达路径）。

### 待查证（重要）

这个结论如果成立，含义很大：

- 如果 `0x9f00d2ac` 真的不可达，那么即使我们写入 `MFS` 魔数，
  **模式分发也不会被激活**——因为调用链本身是断的
- 但设备所有者的 Ghidra 分析显示 `FUN_00005858` 被 `FUN_0000c520` 调用，
  说明按键路径是活的——那么模式参数 `w4` 必然另有来源

**两种可能：**

1. `0x9f00d2ac` 通过我尚未识别的机制被调用（如 `blr` 间接调用、或运行期重定位后
   的指针表、或 U-Boot 的 `initcall` 段用了相对偏移而非绝对地址）
2. 它确实是厂商遗留的死代码，真正生效的是另一条路径

**下一步必须解决**：

- [ ] 扫 `blr`（间接调用）与其来源寄存器，看是否有 `ldr xN, [xM]; blr xN` 模式

- [ ] 换一个已知可达的函数做对照（例如 `printf`/`puts` 的实现），

## ❌ 第二个坐标错误：基址应为 0x9f000000

### 发现过程

前一轮发现「指针表项指向的目标是 0xFF 填充而非字符串」，据此怀疑基址错误。
写 `tools/basecheck.c` 做定量验证：给一个候选基址，统计载荷中 8 字节值
（落在 0x9e000000..0x9fffffff 区间的）有多少指向**可打印字符串的起点**。

结果（12431 个候补值中的命中数）：

| 基址 | 指向可打印串 |
| --- | --- |
| `0x9efffe00` | 229 |
| `0x9f005000` | 189 |
| **`0x9f006000`**（此前用的） | **457** |
| `0x9f007000` | 770 |
| `0x9f008000` | 662 |
| **`0x9f000000`** | **2632** ← 峰值 |

峰值孤立的程度（左右相邻 0x9f001000=103、0x9f002000=259、0x9f003000=137）
足以确认：

```
真实基址 = 0x9f000000
换算     abs(off) = 0x9f000000 + (file_off - 0x200)
```

### 影响范围

| 项 | 影响 |
| --- | --- |
| 所有文档中的**绝对地址** | 需整体 **-0x6000** |
| 「哪个字符串被哪个函数引用」 | **不受影响**（基址无关的相对结构） |
| MFS 魔数、模式表结构、调用链逻辑 | **不受影响** |
| `adrp_xref` / `funcmap` 的相对结果 | **不受影响** |
| 后续找指针表、initcall、命令表 | **必须用新基址** |

### 地址对照（旧 → 新）

```
旧 0x9f038c88  读 miscdata 的 MFS 校验函数   →  新 0x9f032c88
旧 0x9f00d2ac  模式打印函数                  →  新 0x9f0072ac
旧 0x9f00d2b8  调用 MFS 校验的那条 BL        →  新 0x9f0072b8
旧 0x9f09a0f0  模式表（12 字节/项）          →  新 0x9f0940f0
旧 0x9f09a2a0  模式名指针表（8 字节/项）     →  新 0x9f0942a0
旧 0x9f0a1773  模式枚举名字符串              →  新 0x9f09b773
旧 0x9f0a12d7  "Detect the firsrt_mode flag" →  新 0x9f09b0d7
旧 0x9f00d2c8  引用上述字符串的 ADRP         →  新 0x9f0072c8
```

> 注意：`adrp_xref` 的输出是**载荷相对偏移**，与基址无关，因此那部分结果
> （「ADRP@0x72c8 + ADD@0x72cc 引用了 0x9b2d7 处的字符串」）依然有效。

### 方法论补充

这是本项目**第二个**坐标类错误，性质和第一个相同：**用未经验证的初值**。

第一个错误（载荷起点 0x40 vs 0x200）来自「DHTB 头长度 = 载荷起点」的想当然。
第二个错误（基址 0x9f006000）来自早期用**错误偏移**跑出的指针直方图——
也就是说，**第一个错误污染了第二个结论**，而我没意识到依赖关系。

**新增的检验手段**（已固化为 `tools/basecheck.c`）：

```
对每个候选基址，统计「8 字节值 → 可打印串起点」的命中数，取孤立峰值。
```

这个方法不依赖任何格式假设，只用「指针应该指向字符串」这一个可验证的判据，
并且给出了**比值**（2632 / 457 ≈ 5.7 倍）而非绝对值，便于判断置信度。

```

  [8] 0x9f00749c   fd 7b bd a9
  [9] 0x9f007558   fd 7b bf a9
 [10] 0x00000000   ← 表结束
```

**表的读取者**（`adrp_xref` 查 0x9f0b87e0）：

```
ADRP@0x76d8 (X21) + ADD@0x76ec (X0)  [间隔 5]
→ 绝对地址 0x9f0076d8
```

该地址位于 `0x9f007558` 之后的某个函数中，即**分发器**。

### ✅ 推翻「死代码」假设

上一轮提出：`0x9f0072ac`（旧 0x9f00d2ac）既无 BL/B 调用者也不在指针表里，
可能是死代码。

**本轮证伪**：它确实没有 `BL` 调用者，但**它就在 `0x9f0b87e0` 这张函数指针表里**，
而这表被 `0x9f0076d8` 处的代码读取并分发。

```
分发器 @0x9f0076d8
  → 读表 0x9f0b87e0
  → 按模式索引取处理函数
      [2] = 0x9f0072ac  → 内部调 0x9f032c88 做 MFS 校验
```

### 方法教训

**「没有 BL 调用者」不能推出「不可达」。** 我之前用 BL 扫描 + 8 字节指针搜索
两个维度就下了判断，漏掉了「函数指针表」这个维度——而后者恰恰是 U-Boot
这种项目的**主要分发机制**（initcall、命令表、驱动表都是这么做的）。

**新规则**：判断可达性时至少要检查四个维度：

1. `BL` / `B imm26` 直接调用
2. 8 字节绝对指针（含函数指针表）
3. 间接调用（`ldr xN,[xM]; blr xN`）
4. 结构体数组里的函数指针（项大小 ≠ 8，需要按结构体解析）

本轮的 `findtables.c` 解决了第 2 个维度。第 3、4 仍未覆盖。

### 模式表分发循环

```asm
0x9f0076d4  str wzr, [x29, 0x34]              ; i = 0
0x9f0076d8  adrp x21, 0x9f0b8000
0x9f0076dc  ldr w0, [x29, 0x34]               ; 读 i
0x9f0076e0  cmp w0, 0xe                        ; i 与 14 比较
```

### 结构体 +0x40 的字段是什么

`0x9f007868` 返回的结构体指针，其 `+0x40` 处存放 `0x55CC55CC` 或 `0x55DD55DD`，
用来决定启动哪个槽。

### 与「按键失效」的关系

分发器的 `w19`（模式号）**直接来自入参 `w2`**，它对 `> 2` 的情况直接返回 -1。
也就是说：**模式号 <= 2 才走 Android 启动路径，否则进入模式表分发**。

这与之前反汇编 `FUN_00005858` 时看到的 `cmp w4, #1; b.le` 逻辑吻合——
模式号（即 `w4`）在 0~2 之间时按键检测被跳过，**只有在需要选模式时才扫按键**。

⇒ 这条设计是自洽的：正常启动（mode <= 2）不需要按键；只有异常启动才需要。
**厂商没有删掉模式选择，而是把「让设备进入异常启动」的入口拿掉了。**
