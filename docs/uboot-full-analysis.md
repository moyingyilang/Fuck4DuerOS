# U-Boot 全量逆向分析：目标与路线图

> 2026-10-03 立项目标。设备已救回，转入系统性分析阶段。

## 已确立的基础事实（必须遵守）

```
镜像格式      DHTB，头 64 字节，头后 448 字节全零填充
载荷起点      文件偏移 0x200   ★ 曾误判为 0x40，导致 0x1C0 的系统性漏检
载荷末尾      文件偏移 0xe6358
载荷大小      0xe6158 (942,424) 字节
加载基址      0x9f006000
地址换算      abs(off) = 0x9f006000 + (off - 0x200)
```

**验证方式**（必做）：任何新结论都要用端到端对照检验，不能只用同区域类比。

```bash
# 已知字符串必须有引用；载荷相对偏移 = 文件偏移 - 0x200
./adrp_xref uboot_a.img 0x9b2d7    # → ADRP@0x72c8 + ADD@0x72cc
```

## 已确认的关键结论

| 项 | 内容 |
| --- | --- |
| 模式魔数 | `miscdata[0..3]` 小端字：bit0-6 为模式号，bit8-31 须为 `0x53464D`（`'M','F','S'`） |
| 校验函数 | `0x9f038c88` —— 读 miscdata → 校验 → 取模式号 → 查表 |
| 模式表 | `0x9f09a0f0`，12 字节/项，`[+8]` 为启动值 |
| 模式名表 | `0x9f09a2a0`，8 字节/项指针数组 |
| 现状 | 无任何代码写 MFS，故校验恒失败，模式分发永不激活 → 按键被 `w4<=1` 拦住 |
| 按键函数 | Ghidra 中为 `FUN_00005858`（音量上键），模式参数 `w4` 来自上述链路 |

## 方法论（本次教训）

**这个项目已经因为「工具的系统性偏差」犯过一次错**，代价是推翻了正确结论。因此：

1. **验证输入假设**，不要假设格式文档可信。`od` 一行就能发现 0x40~0x200 全零。
2. **阳性对照要端到端**，不能用同区域类比。「另一个字符串有引用」只能证明算子大体可用，不能排除系统性漏检。
3. **阴性结果最多是「不支持」，不能作「否定」**。找不到引用时先怀疑搜索范围与坐标。
4. **每个结论都要留下可复现的验证命令**，写进文档。

### 首批调用链发现

**`0x9f038c88`（读 miscdata 的 MFS 校验函数）只有一个调用者：**

```
0x9f00d2b8  bl → 0x9f038c88
```

该调用者位于函数 `0x9f00d2ac` 内（即打印模式名的那个函数）。

**但对 `0x9f00d2ac` 本身：**

```
BL/B 调用者    0 个
8 字节绝对指针  0 个
```

⇒ `0x9f00d2ac` **可能是死代码**（无任何可达路径）。

### 待查证（重要）

这个结论如果成立，含义很大：

- 如果 `0x9f00d2ac` 真的不可达，那么即使我们写入 `MFS` 魔数，
  **模式分发也不会被激活**——因为调用链本身是断的
- 但设备所有者的 Ghidra 分析显示 `FUN_00005858` 被 `FUN_0000c520` 调用，
  说明按键路径是活的——那么模式参数 `w4` 必然另有来源

**两种可能：**

1. `0x9f00d2ac` 通过我尚未识别的机制被调用（如 `blr` 间接调用、或运行期重定位后
   的指针表、或 U-Boot 的 `initcall` 段用了相对偏移而非绝对地址）
2. 它确实是厂商遗留的死代码，真正生效的是另一条路径

**下一步必须解决**：

- [ ] 扫 `blr`（间接调用）与其来源寄存器，看是否有 `ldr xN, [xM]; blr xN` 模式

- [ ] 换一个已知可达的函数做对照（例如 `printf`/`puts` 的实现），

## ❌ 第二个坐标错误：基址应为 0x9f000000

### 发现过程

前一轮发现「指针表项指向的目标是 0xFF 填充而非字符串」，据此怀疑基址错误。
写 `tools/basecheck.c` 做定量验证：给一个候选基址，统计载荷中 8 字节值
（落在 0x9e000000..0x9fffffff 区间的）有多少指向**可打印字符串的起点**。

结果（12431 个候补值中的命中数）：

| 基址 | 指向可打印串 |
| --- | --- |
| `0x9efffe00` | 229 |
| `0x9f005000` | 189 |
| **`0x9f006000`**（此前用的） | **457** |
| `0x9f007000` | 770 |
| `0x9f008000` | 662 |
| **`0x9f000000`** | **2632** ← 峰值 |

峰值孤立的程度（左右相邻 0x9f001000=103、0x9f002000=259、0x9f003000=137）
足以确认：

```
真实基址 = 0x9f000000
换算     abs(off) = 0x9f000000 + (file_off - 0x200)
```

### 影响范围

| 项 | 影响 |
| --- | --- |
| 所有文档中的**绝对地址** | 需整体 **-0x6000** |
| 「哪个字符串被哪个函数引用」 | **不受影响**（基址无关的相对结构） |
| MFS 魔数、模式表结构、调用链逻辑 | **不受影响** |
| `adrp_xref` / `funcmap` 的相对结果 | **不受影响** |
| 后续找指针表、initcall、命令表 | **必须用新基址** |

### 地址对照（旧 → 新）

```
旧 0x9f038c88  读 miscdata 的 MFS 校验函数   →  新 0x9f032c88
旧 0x9f00d2ac  模式打印函数                  →  新 0x9f0072ac
旧 0x9f00d2b8  调用 MFS 校验的那条 BL        →  新 0x9f0072b8
旧 0x9f09a0f0  模式表（12 字节/项）          →  新 0x9f0940f0
旧 0x9f09a2a0  模式名指针表（8 字节/项）     →  新 0x9f0942a0
旧 0x9f0a1773  模式枚举名字符串              →  新 0x9f09b773
旧 0x9f0a12d7  "Detect the firsrt_mode flag" →  新 0x9f09b0d7
旧 0x9f00d2c8  引用上述字符串的 ADRP         →  新 0x9f0072c8
```

> 注意：`adrp_xref` 的输出是**载荷相对偏移**，与基址无关，因此那部分结果
> （「ADRP@0x72c8 + ADD@0x72cc 引用了 0x9b2d7 处的字符串」）依然有效。

### 方法论补充

这是本项目**第二个**坐标类错误，性质和第一个相同：**用未经验证的初值**。

第一个错误（载荷起点 0x40 vs 0x200）来自「DHTB 头长度 = 载荷起点」的想当然。
第二个错误（基址 0x9f006000）来自早期用**错误偏移**跑出的指针直方图——
也就是说，**第一个错误污染了第二个结论**，而我没意识到依赖关系。

**新增的检验手段**（已固化为 `tools/basecheck.c`）：

```
对每个候选基址，统计「8 字节值 → 可打印串起点」的命中数，取孤立峰值。
```

这个方法不依赖任何格式假设，只用「指针应该指向字符串」这一个可验证的判据，
并且给出了**比值**（2632 / 457 ≈ 5.7 倍）而非绝对值，便于判断置信度。

```

  [8] 0x9f00749c   fd 7b bd a9
  [9] 0x9f007558   fd 7b bf a9
 [10] 0x00000000   ← 表结束
```

**表的读取者**（`adrp_xref` 查 0x9f0b87e0）：

```
ADRP@0x76d8 (X21) + ADD@0x76ec (X0)  [间隔 5]
→ 绝对地址 0x9f0076d8
```

该地址位于 `0x9f007558` 之后的某个函数中，即**分发器**。

### ✅ 推翻「死代码」假设

上一轮提出：`0x9f0072ac`（旧 0x9f00d2ac）既无 BL/B 调用者也不在指针表里，
可能是死代码。

**本轮证伪**：它确实没有 `BL` 调用者，但**它就在 `0x9f0b87e0` 这张函数指针表里**，
而这表被 `0x9f0076d8` 处的代码读取并分发。

```
分发器 @0x9f0076d8
  → 读表 0x9f0b87e0
  → 按模式索引取处理函数
      [2] = 0x9f0072ac  → 内部调 0x9f032c88 做 MFS 校验
```

### 方法教训

**「没有 BL 调用者」不能推出「不可达」。** 我之前用 BL 扫描 + 8 字节指针搜索
两个维度就下了判断，漏掉了「函数指针表」这个维度——而后者恰恰是 U-Boot
这种项目的**主要分发机制**（initcall、命令表、驱动表都是这么做的）。

**新规则**：判断可达性时至少要检查四个维度：

1. `BL` / `B imm26` 直接调用
2. 8 字节绝对指针（含函数指针表）
3. 间接调用（`ldr xN,[xM]; blr xN`）
4. 结构体数组里的函数指针（项大小 ≠ 8，需要按结构体解析）

本轮的 `findtables.c` 解决了第 2 个维度。第 3、4 仍未覆盖。

### 模式表分发循环

```asm
0x9f0076d4  str wzr, [x29, 0x34]              ; i = 0
0x9f0076d8  adrp x21, 0x9f0b8000
0x9f0076dc  ldr w0, [x29, 0x34]               ; 读 i
```

`0x9f007868` 返回的结构体指针，其 `+0x40` 处存放 `0x55CC55CC` 或 `0x55DD55DD`，
用来决定启动哪个槽。

**待查**：

- [ ] `0x9f007868` 返回的是什么结构体（很可能是 `boot_flow` / `slot_suffix` 相关）
- [ ] `0x55CC55CC` / `0x55DD55DD` 的写入方是谁（是否来自 misc 的 BCB 或 GPT 的

- [ ] 这两个魔数是否就是设备所有者记忆中的「固定常量」（他记得是 `0x77777` 一类，

### 与「按键失效」的关系

分发器的 `w19`（模式号）**直接来自入参 `w2`**，它对 `> 2` 的情况直接返回 -1。
也就是说：**模式号 <= 2 才走 Android 启动路径，否则进入模式表分发**。

这与之前反汇编 `FUN_00005858` 时看到的 `cmp w4, #1; b.le` 逻辑吻合——
模式号（即 `w4`）在 0~2 之间时按键检测被跳过，**只有在需要选模式时才扫按键**。

⇒ 这条设计是自洽的：正常启动（mode <= 2）不需要按键；只有异常启动才需要。
**厂商没有删掉模式选择，而是把「让设备进入异常启动」的入口拿掉了。**

### 结构解读

**三段式：**

```
阶段一  遍历全局处理器表 0x9f0b87e0（10 项，NULL 结尾）
        每个处理函数返回 0 = 未处理（继续），非 0 = 已处理（停止）
        ↓
阶段二  打印 "enter boot mode %d"，w19 是选中的模式号
        ↓
阶段三  用栈上缓冲区 x20 = x29+0x38（0xd8 字节，已 memset 清零）
        作为最终分发表，索引 buffer[mode]
        若 mode-2 > 0x18 或表项为 NULL → 调 0x9f03d6a8 后死循环
```

**关键洞察**：阶段一的 10 个处理函数不只是「处理」，它们会往**栈上的
0xd8 字节缓冲区里登记各自的处理器**，阶段三再按模式号索引调用。

这是一个**两阶段分发表构建 + 索引**的设计：

```
全局表 0x9f0b87e0（静态，10 项）
    ↓ 依次调用，各自往栈表登记
栈表 x29+0x38（动态，0xd8 = 27 项 × 8 字节）
    ↓ 按 mode 索引
最终处理函数
```

> 栈表 `0xd8 / 8 = 27` 项，而阶段三的边界检查是 `mode - 2 <= 0x18`（24），
> 即**合法模式号是 2 ~ 26**，共 25 个。与 27 项容量基本吻合
> （可能是 2 项预留或索引从 0 开始留头）。

### 相关字符串

```

0x9f09b49a : "bad combination can not boot"
0x9f09b4cc : "cboot"
```

### 与「按键失效」的关系（进一步收窄）

阶段一的第一项 `0x9f007228` 和第三项 `0x9f0072ac` 都涉及模式读取。
`0x9f0072ac` 内部调 `0x9f032c88` 做 MFS 校验，校验失败就返回 0（未处理），
于是链路会继续走后面的处理器。

**这意味着：即使 MFS 校验失败，后面还有别的处理器可能命中。**
所以「写入 MFS 是否能改变行为」取决于后续处理器是否也依赖该字段。

| 序 | 地址 | 探测来源 | 字符串 |

| 1 | `0x9f007228` | **miscdata 的 `first_mode`** | `Detect the firsrt_mode flag in the miscdata partition` |
| 2 | `0x9f007290` | **misc 的 recovery 消息** | `Detect the recovery message in the misc partition` |
| 3 | `0x9f0072ac` | 同上（这段的延续 / 或首个处理器的另一半） | 同上 |
| 4 | `0x9f0072fc` | 关机充电 | `in charging during shutdown the devices` |
| 5 | `0x9f007330` | 充电器连接 / **按键** | `Charger connected`、`Keypad trigger to recovery` |
| 6 | `0x9f0073dc` | 看门狗 + 关机闹钟 | `Watchdog reset pending and poweroff alarm` |
| 7 | `0x9f0071c8` | 看门狗异常 | `Watchdog reset pending but Shutdown alarm is abnormal` |
| 8 | `0x9f007440` | RTC 闹钟到期 | `RTC poweroff alarm expiry` |

| 10 | `0x9f007558` | **按键触发 recovery** | `Keypad trigger to recovery` |

### 完整的启动模式探测链

```
for handler in [0x9f007228, 0x9f007290, 0x9f0072ac, 0x9f0072fc,
                0x9f007330, 0x9f0073dc, 0x9f0071c8, 0x9f007440,
                0x9f00749c, 0x9f007558]:
    ret = handler()
    if ret != 0: return ret        # 命中，结束
return 0                            # 全部未命中
```

**探测顺序（按代码顺序）：**

1. `miscdata` 的 `first_mode` 字段
2. `misc` 分区的 recovery 消息
3. 关机充电状态
4. 充电器连接状态
5. **按键触发 recovery** ← 音量键
6. 看门狗复位 + 关机闹钟
7. 看门狗复位但关机闹钟异常
8. RTC 关机闹钟到期

### 对「按键失效」的最终解释

**按键探测确实在链上（第 5 项），但它不是第一个被检查的。**

前面四项（`first_mode`、misc recovery 消息、充电状态、充电器）**任意一个命中**
就会提前返回，不再执行到按键探测。

而设备正常启动时：

```
first_mode    → MFS 魔数不匹配 → 未命中，继续
misc recovery → BCB 是空的     → 未命中，继续
充电状态      → 正常            → 未命中，继续
充电器        → 未接            → 未命中，继续
按键          → ★ 本该在这里检查
```

所以理论上按键探测**应该**会执行到。那么「按键无效」的原因就不在探测链，
而在**探测链之前**——即 `FUN_00005858` 里那个 `cmp w4, #1; b.le` 的提前返回。

**两者并不矛盾**：`FUN_00005858` 是**按键本身的初始化/扫描函数**，
它在模式参数 `w4 <= 1` 时直接跳过扫描；而探测链的第 5 项调用它时，
如果 `w4 <= 1` 就会拿到「无按键」的结果。

⇒ **`w4` 才是根因。** 而 `w4` 来自分发器的 `w2`（模式号）。
而分发器的 `w2` 又来自……**它的调用者**。

这就是下一轮必须回答的问题：**谁调用 `0x9f00763c`，传的 `w2` 是什么。**

### 与 MFS 的关系（明确了）

`first_mode` 是探测链的**第一项**。所以：

- 写入 MFS 魔数 → 第 1 项命中 → **直接返回模式号，整个链短路**
- 不需要管按键、不需要管 BCB、不需要管充电状态

**这确认了「写 4 字节 miscdata」这条路的价值**：它是优先级最高的探测源。

但前提是**分发器确实被调用**，且 `w2` 的取值不影响。

### 待查

- [ ] **谁调用分发器 `0x9f00763c`，`w2` 是什么** ← 最关键
- [ ] `first_mode` 探测函数（`0x9f007228`）返回的模式号是多少
- [ ] 探测链的返回值如何映射到阶段三的 `mode-2` 索引

## 进度：P1 —— 分发器身份确认：`cboot` 命令的处理函数（Round 9）

### 答案

分发器 `0x9f00763c` **不是普通函数，它是 U-Boot 命令表中一条命令的处理函数**。

```bash
./findtables uboot_a.img 9f000000 3
→ 0x9f0c93b8 4  0x9f00763cP 0x9f09b4d2 0x9f09b4e3 0x9f09eb88
```

```bash
./dumptbl uboot_a.img 9f000000 9f0c93b8 8
  [0] 0x9f0c93b8 = 0x9f00763c    ← handler（分发器）
  [1] 0x9f0c93c0 = 0x9f09b4d2    → "choose boot mode"
  [2] 0x9f0c93c8 = 0x9f09b4e3    → "mode: "
  [3] 0x9f0c93d0 = 0x9f09eb88    → "cls"
  [4] 0x9f0c93d8 = 0x100000001
  [5] 0x9f0c93e0 = 0x9f00f0ac    ← 下一条命令的 handler
  [6] 0x9f0c93e8 = 0x9f09eb8c    → "clea…"
```

**这是 U-Boot 命令表的标准布局**（`handler` + `name` + `usage` + …）。

### `w2` 的来源链

设备的环境变量里有（早前已确认）：

```
bootcmd = "cboot normal"
preboot = "role"
```

于是：

```
U-Boot 启动 → 执行 bootcmd → "cboot normal"
    ↓
cboot 命令解析参数 "normal"
    ↓
模式名 → 数字（NORMAL_MODE = 2，按 0x9f09b773 处枚举表顺序）
    ↓
w2 = 2 → 传入分发器 0x9f00763c
```

**⇒ `w2` 就是 `cboot` 命令的模式参数。**

### 由此得到一个必须解释的矛盾

若 `w2 = 2`（normal）：

```asm
; 分发器
0x9f007668  cmp w19, 2
0x9f00766c  b.gt 0x9f007768       ; w19=2 不大于 2 → 不跳，继续 ✓

; FUN_00005858（按键扫描）
cmp w4, #1
b.le  返回 -1                      ; w4=2 > 1 → 不提前返回 ✓
```

**两条路径都指向「按键探测应该被执行」，但实测按键无效。**

可能的解释（待验证）：

1. **`w4` 与 `w2` 不是同一个值**。`w4` 可能来自另一个来源——比如
   `0x9f0f0b80 + 0x40` 那个结构体字段，或者探测链的某个中间结果，
   而不是直接来自 `w2`。
2. **`cboot normal` 的 "normal" 没有映射到 2**。模式名解析可能失败或
   映射到别的数字（例如 `vlx`、`caliberation` 等非常规模式）。
3. **`FUN_00005858` 的 `w4` 是经过变换的**。设备所有者的 Ghidra 分析显示
   `FUN_00005858` 被 `FUN_0000c520` 调用，传入的 `param_13` 是
   `param_11 - 1`——**减了 1**。若 `param_11 = 2` 则 `w4 = 1`，
   `cmp w4, #1; b.le` **成立** → 提前返回 → 按键被跳过！

**第 3 条最有可能**：`param_11 - 1` 意味着传入的不是模式号本身，而是
模式号减一。`2 - 1 = 1`，恰好落在 `b.le` 的捕获范围内。

> 这与设备所有者的 Ghidra 记录吻合：
> 「`FUN_00005858` 被 `FUN_0000c520` 调用，传入的 `param_13` 值为 `param_11 - 1`」

### 待验证

- [ ] 反汇编调用 `FUN_00005858` 的 `FUN_0000c520`（需换算到新基址坐标）
- [ ] 确认 `param_11` 与 `param_13` 的真实关系是否就是减一
- [ ] 若确认为减一，则 `NORMAL_MODE = 2 → w4 = 1` 必然跳过按键扫描，
      这就是**设计上的必然结果**，而非 bug 或厂商裁剪
- [ ] 那么「按键进入 recovery」只可能在某些 `param_11 >= 3` 的场景下成立
      —— 即**只有从异常启动路径进入时，按键才被扫描**

### 这个结论的含义

如果上述成立，则：

**按键不是"失效"，而是"设计上就只在异常启动时才生效"。**
正常开机（`cboot normal`）永远不扫按键，这是**预期行为**。

而用户想要的「按住音量键进 fastboot」，在这台设备上**需要先让设备进入
异常启动状态**（例如 BCB 里写了 recovery、或 miscdata 的 first_mode 命中）
——这正好解释了为什么 `adb reboot bootloader` 能进、而按键不能。

## 进度：P1/P7 —— 按键子系统反汇编（Round 10）

### 定位方法

`[gpio keys] init skip!` 与 `[eic keys] volumeup` 两个字符串的引用点：

```bash
./adrp_xref uboot_a.img 0x9a62c
→ ADRP@0x4a44 (X0) + ADD@0x4a4c (X0)     ; 绝对地址 0x9f004a44

./adrp_xref uboot_a.img 0x9a644
→ ADRP@0x4a80 (X0) + ADD@0x4a9c (X0)     ; 绝对地址 0x9f004a80 / 0x9f004a9c
```

> 注意：`adrp_xref` 的目标参数是**载荷相对偏移**（`abs - 0x9f000000`），
> 不是文件偏移。这一轮在这里又踩了一次。

### 两个相关函数

**函数 A @ `0x9f004a24`** —— GPIO 按键初始化

```asm
0x9f004a24  stp x29, x30, [sp, -0x10]!
0x9f004a28  mov w1, 0x7c
0x9f004a2c  mov x29, sp
0x9f004a30  mov x0, 0
0x9f004a34  bl  0x9f04caf0                ; 某个初始化
0x9f004a38  mov w1, 0x7c
0x9f004a3c  mov x0, 0
0x9f004a40  bl  0x9f04ca2c
0x9f004a44  adrp x0, 0x9f09a000
0x9f004a4c  add  x0, x0, 0x62c             ; "[gpio keys] init skip!"
0x9f004a50  b    0x9f01270c               ; 打印
```

**函数 B @ `0x9f004a54`** —— EIC 读取音量上键

```asm
0x9f004a54  stp x29, x30, [sp, -0x20]!
0x9f004a58  mov w0, 0xa4                    ; ★ EIC 通道 0xa4
0x9f004a64  bl  0x9f04cefc                  ; EIC 配置
0x9f004a68  mov x0, 0xbb8
0x9f004a6c  bl  0x9f07f33c                  ; 延时 3000（0xbb8 ms）
0x9f004a70  mov w0, 0xa4
0x9f004a74  bl  0x9f04ce80                  ; ★ sprd_eic_get(0xa4)
0x9f004a78  cmp w0, wzr
0x9f004a7c  b.ge 0x9f004aa8                 ; >= 0 → 成功路径
0x9f004a80  adrp x0, 0x9f09a000
0x9f004a88  add  x1, x1, 0x8e0              ; 另一字符串（"%s: %s"？）
0x9f004a8c  add  x0, x0, 0x247
0x9f004a90  mov w19, 0
0x9f004a94  bl  0x9f01270c                  ; 打印前半
0x9f004a98  adrp x0, 0x9f09a000
0x9f004a9c  add  x0, x0, 0x644              ; "[eic keys] volumeup : … ERROR!"
0x9f004aa0  bl  0x9f01270c                  ; 打印后半

0x9f004aa8  mov  w19, 0x73                  ; 's'
0x9f004aac  csel w19, w19, wzr, ne
```

### ⚠️ 这是第二个独立的根因

之前（Round 9）的结论是：`w4 <= 1` 导致按键扫描被跳过（设计行为）。

**现在发现还有一层：即使扫描被执行，`sprd_eic_get(0xa4)` 本身也可能失败。**

```
[gpio keys] init skip!                     ← 初始化被跳过
[eic keys] volumeup : sprd_eic_get ERROR!   ← 读取失败
```

两者是**不同位置的两个问题**：

| 层 | 位置 | 现象 | 性质 |
| --- | --- | --- | --- |
| 逻辑层 | `FUN_00005858` 的 `cmp w4,#1; b.le` | 整个扫描被跳过 | 设计行为（正常启动不扫按键） |
| 驱动层 | `0x9f004a54` 的 `sprd_eic_get(0xa4) < 0` | EIC 通道读不到 | **可能是真故障** |

### 待查

- [ ] `0xa4` 是否确实是音量上键的 EIC 通道号
- [ ] `sprd_eic_get` 返回负值的具体原因（通道未配置？EIC 未初始化？）
- [ ] 函数 A 打印 "init skip!" 的原因——它调用了 `0x9f04caf0` 与 `0x9f04ca2c`
      但没有检查返回值就直接打印跳过
- [ ] 函数 A 与函数 B 的调用关系（谁先谁后）
- [ ] `0x9f0908e0` 处那个字符串是什么（函数 B 打印的前半部分）

### 意义

如果驱动层确实有故障（EIC 读不到），那么**即使解决了 `w4` 的门控，按键仍然无效**。
这意味着「按住音量键进 fastboot」在这台设备上**可能根本不可行**，而不只是被设计隐藏。

而 BCB 那条路（`boot-recovery` + `--fastboot`）已经实测可用，且不依赖按键——
**这是两条独立的路，BCB 那条至少是通的。**

## 进度：P7 —— 按键函数的调用上下文（Round 11）

### 两个函数的调用者

```bash
./callgraph uboot_a.img 9f000000 9f004a24
  0x9f00478c  bl → 0x9f004a24          # 唯一调用者

./callgraph uboot_a.img 9f000000 9f004a54
  0x9f0074cc  bl → 0x9f004a54          # ★ 模式处理链的第 9 项
  0x9f028df0  bl → 0x9f004a54
  0x9f02a0a4  bl → 0x9f004a54
  0x9f02cf44  bl → 0x9f004a54
  0x9f02d020  bl → 0x9f004a54
```

### 函数 A 的调用上下文：board init 序列

```asm
0x9f00476c  stp x29, x30, [sp, -0x10]!      ; 函数入口
0x9f004770  mov x29, sp
0x9f004774  bl  0x9f007868                   ; 取全局结构体 0x9f0f0b80
0x9f004778  bl  0x9f006fec
0x9f00477c  bl  0x9f052568
0x9f004780  bl  0x9f03ee54
0x9f004784  bl  0x9f0528a4
0x9f004788  bl  0x9f052ddc
0x9f00478c  bl  0x9f004a24                   ; ★ GPIO 按键初始化（序列末尾）
0x9f004790  mov w0, 0
0x9f004794  ldp x29, x30, [sp], 0x10
0x9f004798  ret
```

**这是一个 7 步的板级初始化序列**，按键初始化排在最后。

### 函数 B 只在模式探测链中被调用

`0x9f0074cc` 位于 `0x9f00749c` 与 `0x9f007558` 之间——即模式处理表的**第 9 项**
（`0x9f00749c`，对应「关机充电」类探测）。

**⇒ EIC 读取（函数 B）不是启动时无条件执行的，只在模式探测链走到第 9 项时才调用。**

另有 4 个调用者（`0x9f028df0` / `0x9f02a0a4` / `0x9f02cf44` / `0x9f02d020`），
应该属于充电管理子系统。

### 由此修正 Round 10 的推断

Round 10 说「驱动层可能真有故障」。现在看：

- `[eic keys] volumeup : … return ERROR!` 只在**探测链走到第 9 项**时才可能打印
- 而正常启动时前 8 项都可能命中（`first_mode`、misc recovery、充电状态…）
- 若前面任一项命中，链就短路，**根本不会走到第 9 项**

**⇒ 观察到那条 ERROR 日志，说明探测链确实走到过第 9 项**——即前面的探测全部未命中。
这反而证明：**链是活的、在正常执行的**。

### 待验证

      与 `0x9f04ca2c(0, 0x7c)` 后没有检查返回值。需看这两个函数是否
      自身打印错误、而函数 A 只是紧跟着的固定提示
- [ ] `0x7c`（124）参数的含义

### 阶段性判断

到目前为止，按键相关的三层都已定位：

```
1  board init 序列末尾调用 GPIO 按键初始化 (0x9f004a24)
2  EIC 读取 (0x9f004a54) 只在模式探测链第 9 项被调用
3  FUN_00005858 的 cmp w4,#1; b.le 控制是否扫描
```

**「按键能否生效」取决于第 3 层的 w4**，而 w4 来自分发器的 w2（即 `cboot` 命令参数）。
这条链已经完整，剩下的只是确认 `param_11 - 1` 这个变换。
